**커밋 마커 `[done]` + 머지 게이트**
- 요청받은 구현이 **끝났으면** 제목 끝에 `[done]`. WIP·중간 저장엔 **안 붙인다**
- `[done]` = "구현 끝났다, 판정해라" — **사실 선언이지 예측이 아니다.** "머지해도 될 것 같다"를 스스로 판단하지 마라
- **`[done]` 은 트리거가 아니다.** feature 브랜치 커밋은 어떤 훅도 돌리지 않는다. dev 세션에게 보내는 선언일 뿐
- **트리거는 dev 로 머지되는 순간 하나다.** dev 세션이 `.githooks/ticket.sh merge <브랜치>` 를 돌리면 훅이:
  - `pre-merge-commit` → **머지 결과 트리**에서 `verify.sh`. 실패면 머지 커밋을 만들지 않는다 (`ticket.sh merge` 가 `merge --abort` 까지)
  - `post-merge` → 리뷰 보고서 `dev/.tickets/<slug>/review-<sha>.md` + 큐 한 줄
  - **충돌이 나면 위 두 훅은 안 뜬다**(git 동작). 사람이 해결 후 `git commit` 하면 `pre-commit`(같은 verify) + `post-commit`(같은 보고서)이 대신 돈다
- verify 실패면 **머지 안 되고** `dev/.tickets/<slug>/verify-<sha>.log`(sha = 머지 대상 브랜치 팁)에 남는다. 훅이 Orca 카드로 알림
- **dev 에 사람이 직접 만든 비머지 커밋(docs·e2e 수정)은 보고서를 만들지 않는다** — 사소한 변경만 오는 자리다. dev 에 실질 변경이 들어오는 경로는 머지 하나
- **dev 워크트리에 `merge.ff=false` 필수** — ff 머지는 `pre-merge-commit` 을 건너뛰어 게이트가 우회된다. `ticket.sh merge` 는 `--no-ff` 고정
- 훅 본체는 `.githooks/dev-sync.sh` 하나, 4개 훅 파일은 모드만 넘기는 shim. 점검: `sh .githooks/dev-sync.sh --selftest`
- 형식: `<type>(<scope>): <설명> [done]` / type: feat·fix·docs·style·refactor·test·chore / 본문에 왜(Why)·무엇을(What)
- **완료 통지(`worker_done`) 쓰는 규칙** — 워크트리 에이전트용. Orca 프리앰블이 "3문장 요약"을 요구하므로 그 3문장을 이렇게 쓴다:
  - 반드시 포함: **브랜치명 · 커밋 sha · `[done]` 붙였는지**. dev 세션이 `ticket.sh merge <브랜치>` 를 돌리는 데 필요한 값이 그것뿐이다
  - **테스트·타입체크 결과를 사실로 단정하지 마라.** 판정은 머지 시점 `verify.sh` 종료코드가 한다. 로컬에서 돌렸으면 "로컬에서 돌려봤다" 로 적는다
  - 남은 것·못 한 것·임의로 정한 것은 반드시 적는다 — 그것이 재요청 판단의 유일한 입력이다
  - 실패도 `worker_done` 이다 (`--subject "Failed: <이유>"`). 조용히 끝내면 dev 세션이 영원히 기다린다

**티켓 워크플로 (dev = 허브)**
- **dev 세션은 리뷰하지 않는다.** diff 판단은 훅의 리뷰 에이전트가 이미 했다. dev 세션 역할 = 티켓 정의 + 보고서 요약 + 라우팅
- **사람에게 가는 보고는 전부 `writing-korean-explainers` 스킬로 쓴다** — 머지 결과 요약, 게이트 실패 보고, `wait` 결과 정리, `close` 종합 전달이 모두 해당한다. 규칙은 스킬의 `규모가 작은 보고` 절: 결론을 첫 줄에, 기계가 판정한 것은 한 줄로 접고, 마지막 줄에 선택지 두 개
  - **리뷰 보고서를 그대로 붙여넣지 마라.** 보고서는 dev 세션이 읽을 입력이고, 사람이 읽을 것은 거기서 판단이 필요한 부분만 남긴 5~10줄이다. 붙여넣으면 요약을 사람이 다시 하게 된다
  - 지적은 **기능 영향 있음 / 없음**으로 갈라 제시한다. 그 축이 사람이 재요청 여부를 정하는 기준이다
  - 마지막 줄 선택지는 보통 `재요청 / 마무리` 두 개다. 어느 쪽을 권하는지 한 줄로 밝히되 결정하지는 않는다
- 산출물은 **티켓 폴더 하나에 모인다**: `.tickets/<slug>/` = `spec.html`(사람) + `verify-<sha>.log`(기계) + `review-<sha>.md`(판단, 라운드별). 인덱스는 `.tickets/queue.md` 하나 — 큐는 dev 전체를 대표해야 하므로 티켓 폴더 안에 넣지 않는다. 한 줄 형식은 `- [브랜치](링크) 시각 — <spec.html 의 h1>` 이라 큐만 훑어도 무슨 작업이었는지 보인다(스펙 제목이 없으면 첫 커밋 제목이 들어간다)
- **`close` 가 라운드 리뷰들을 `review.md` 하나로 접는다** — 라운드 원본은 `<slug>/rounds/` 로 이동(기록 유지), 큐의 라운드 줄들도 종합 1줄로 교체. 재요청이 3~4라운드 돌면 같은 티켓 리뷰가 큐에 흩어져 티켓 단위로 읽을 수 없다. 종합 시점이 `close` 인 이유 = 그때 dev 가 티켓의 최종 코드다(지적이 아직 살아있는지 현재 코드로 확인 가능)
- 브랜치를 못 알아낸 머지의 보고서는 `.tickets/_dev/`. **실패는 큐에 올리지 않는다** — "큐에 있는 것 = verify 통과 + 머지 완료"가 큐를 신뢰하는 근거다
- **워크트리 에이전트의 완료 통지는 깨우기 신호다** (읽는 쪽 규칙 — 쓰는 쪽 규칙은 위 `worker_done` 항목). 브랜치·커밋 sha·`[done]` 여부만 취하고, "잘 돌아간다"·"테스트 통과"는 판정 근거로 쓰지 않는다 (판정은 머지 시점 `verify.sh`)
- **티켓 1개 = dev 세션 1개.** 마무리하면 세션 종료. dev를 상시 코디네이터로 만들면 컨텍스트가 오염된다
- 순서: `ticket.sh new` → `wait` → **`merge`** → (보고서 요약) → `close`. 발사·대기·머지·재요청·정리 전부 `.githooks/ticket.sh` (dev 워크트리에서만)
- **브랜치명은 `new` 출력의 실제 이름을 쓴다** — orca 가 `feat/x` 를 `feat-x` 로 정규화한다. 요청한 이름으로 `merge` 하면 브랜치를 못 찾는다
- **재요청 본문은 파일로 넘긴다** (`send <브랜치> <파일>`). 재요청에도 **손대지 말 것**을 적어라 — 스펙에서 정한 결정이 리뷰 지적으로 다시 올라오면 워커가 "고쳐야 할 것"으로 읽는다
- **리뷰 보고서 지적은 자동 재요청 사유가 아니다.** 라운드마다 새 지적이 나오므로(주석·테스트 형태 같은 기능 무영향 건) 멈출 지점은 사람이 정한다. dev 세션은 "기능 영향 있음/없음"으로 갈라 제시만 한다
- **`[done]` 통지를 받으면 머지는 즉시 돌린다 — 사람 승인을 앞에 두지 않는다.** 머지 전에는 사람이 판단할 재료가 없다(보고서는 머지 후 생성). 게이트가 실패하면 머지 커밋이 안 만들어지고 dev 는 손 안 타므로 위험도 없다. **사람의 결정 지점은 머지 뒤**(재요청 vs 마무리)
  - 예외 — 머지하지 않는다: 통지가 `Failed: <이유>` 이거나 `[done]` 이 없을 때(중간 보고·막힘). 이유를 사람에게 보고하고 `ticket.sh send` 로 지시를 다시 보낸다
- **워커에게 가는 모든 말은 `ticket.sh send` 하나다** — 재요청이든 질문(`decision_gate`)에 대한 답이든. `orca orchestration reply` 를 쓰지 마라: 그것은 메시지만 저장할 뿐 **턴이 끝난 워커를 깨우지 않는다**. `worker_done` 을 보낸 워커는 대기 상태가 아니라 턴이 끝난 상태이고, 질문 통지는 그 뒤에 도착하는 일이 흔하다(도착 순서 역전). 답장이 조용히 유실되고 `wait` 가 영원히 빈손이 된다
- **통지 대기는 `ticket.sh wait` 하나로만 한다** — `orca orchestration check` 를 직접 부르지 마라. `--terminal` 을 빼면 메일박스가 열리지 않아 **에러 없이 항상 빈손**이고, 통지는 사람이 ESC 로 턴을 끊을 때만 보인다(그 시점엔 워커가 이미 끝나 있다). `wait` 는 `ORCA_PANE_KEY` 로 자기 핸들을 찾아 명시하고, 못 찾으면 헛돌지 않고 죽는다
- **`wait` 가 2회 연속 빈손이면 워커가 멈춘 것이다.** 계속 기다리지 마라 — `git log -1 <브랜치>` 로 커밋이 안 늘었으면 `ticket.sh send` 로 지시를 다시 보낸다
- **티켓 스펙 초안은 사람이 쓴다.** dev 세션은 빈 슬롯을 지적하고 채우도록 되묻는다 — 초안을 대신 쓰면 계획이 위임된다. 판정 기준·5슬롯 템플릿은 `writing-ticket-specs` 스킬
