# 티켓 워크플로 스캐폴드

LLM 워커를 격리된 워크트리에서 병렬로 돌리면서, `dev` 브랜치에는 검사를 통과한 코드만 들어가게
만드는 구성이다. 실제 운영 중인 프로젝트에서 돌고 있는 것을 그대로 뽑았다 (2026-08-03 기준).

```
workflow-scaffold/
  install.sh                            설치 (여러 번 돌려도 안전하다)
  githooks/
    dev-sync.sh                         훅 본체 — 모드 4개 + --selftest
    pre-merge-commit  pre-commit        게이트. 본체를 호출하는 2~3줄
    post-merge  post-commit             보고서. 본체를 호출하는 2~3줄
    ticket.sh                           티켓 라이프사이클 (new/wait/merge/send/close)
    verify.sh                           게이트가 실행하는 검사 ← 프로젝트마다 교체한다
    reviewer-prompt.md                  머지별 리뷰 프롬프트 ← '대상'·'체크 대상'을 프로젝트마다 교체한다
    closing-prompt.md                   close 종합 프롬프트
  templates/
    CLAUDE-workflow-section.md          워크트리 상위 CLAUDE.md 에 붙일 규칙
    spec.html                           티켓 스펙 5슬롯
  skills/                               → dev 워크트리 .claude/skills/ 로 설치한다
    writing-ticket-specs/               스펙 5슬롯 검토
    writing-korean-explainers/          사람에게 하는 보고·설명 작성
    writing-session-worklogs/           세션 작업 기록 → docs/worklog/. 전역 스킬이라 설치 대상이 아니다
                                        (~/.claude/skills/ 에 심링크로 건다 — 아래 '전역 스킬' 절)
    building-project-llm-wiki/          프로젝트 문서를 LLM 위키(raw·위키·해시 대장·ingest 훅)로 세운다. 전역 스킬
```

# 어떻게 동작하는가

## 전체 구조

워커 에이전트는 각자 별도의 git 워크트리를 하나씩 받는다. 워크트리끼리는 격리돼 있어서, 그 안에서
무슨 커밋을 하든 다른 쪽에는 영향이 없다. 작업이 끝난 코드는 결국 `dev` 브랜치 하나로 모이는데,
그 입구에 검사 스크립트 하나가 걸려 있다.

```
 워크트리 A     워크트리 B     워크트리 C      ← 여기서 하는 커밋은
   (워커)         (워커)         (워커)           훅을 하나도 실행하지 않는다
      └──────────────┼──────────────┘
                     │  git merge
          ┌──────────▼──────────┐
          │  게이트: verify.sh  │   ← dev 로 들어가는 길은 이것 하나뿐
          └──────────┬──────────┘
                     │ 통과한 것만
     ════════════════▼════════════════  dev 브랜치
                     │
             리뷰 보고서 + 큐에 한 줄
```

게이트에서는 사람도 LLM도 판단하지 않는다. `verify.sh` 를 실행해서 종료 코드가 0이면 머지를
통과시키고, 0이 아니면 막는다. 리뷰 에이전트는 머지가 끝난 다음에 붙기 때문에 애초에 머지를
막을 수단이 없다.

## 역할 분담

LLM은 자기가 작업을 끝냈다는 것은 알지만, 그 코드가 안전한지는 모른다. 그래서 워커가 커밋
메시지에 붙이는 `[done]` 은 "머지해도 된다"는 판단이 아니라 "구현을 끝냈으니 판정해달라"는
신고에 가깝다. 판정은 머지할 때 `verify.sh` 가 한다.

| 역할 | 하는 일 | 할 수 없는 일 |
|---|---|---|
| 사람 | 무엇을 만들지 정하고, 보고서를 읽고 다시 시킬지 끝낼지 결정한다 | — |
| dev 세션 | 워크트리를 만들고, 완료를 기다리고, 머지를 실행하고, 정리한다 | 판정하지 않는다. 리뷰도 하지 않는다 |
| 훅 | `verify.sh` 를 돌리고 리뷰 보고서를 만든다 | 무엇을 만들지 정하지 않는다 |
| 워커 | 구현하고 커밋하고 완료 통지를 보낸다 | 자기 코드를 승인할 수 없다 |

## 머지할 때 순서대로 일어나는 일

```
 ① 워커가 `[done]` 을 붙여 커밋한다        ← 워크트리 안이라 훅이 안 돈다
 ② 워커가 완료 통지를 보낸다
 ③ dev 세션이 ticket.sh merge 를 실행한다
 ④ pre-merge-commit 훅이 verify.sh 를 돌린다      ★ 판정은 여기서만
      ┌───────────┴───────────┐
   종료 코드 0              0 이 아님
      │                       │
  머지 커밋이 만들어진다    머지 커밋이 만들어지지 않는다
      │                    → merge --abort 로 dev 를 되돌린다
      ▼                    → 검사 로그만 남는다
  post-merge 훅이
  보고서 + 큐에 한 줄
```

여기서 두 가지를 짚어둘 만하다.

첫째, 검사가 실행되는 시점은 **머지가 진행 중인 dev 워크트리**다. 즉 검사 대상이 머지된
결과물이다. 브랜치에서만 돌려보면 통과하는데 dev와 합치면 깨지는 충돌은 이 위치에서만 잡힌다.

둘째, 리뷰가 실패해도 머지는 그대로 유지된다. 이때 보고서는 기계 검증 블록까지만 남고 큐에는
줄이 붙지 않는다. 그래서 큐는 성공한 것들의 명단일 뿐이고, dev의 현재 상태를 전부 보여주지는
않는다.

## 훅이 네 개인 이유

머지가 커밋으로 마무리되는 방식이 두 가지이기 때문이다.

충돌이 없으면 git이 머지 커밋을 알아서 만들고, 이때 `pre-merge-commit` 과 `post-merge` 가
실행된다. 반면 충돌이 나면 git은 중간에 멈추고, 사람이 파일을 고친 뒤 직접 `git commit` 으로
마무리한다. 이 경로에서는 앞의 두 훅이 아예 실행되지 않는다. 그래서 같은 일을 하는
`pre-commit` 과 `post-commit` 이 한 짝 더 있다.

앞쪽 둘은 같은 `verify.sh` 를 돌리고, 뒤쪽 둘은 같은 보고서를 만든다. 덕분에 사람이 충돌을
직접 해결해서 넣은 코드도 검사를 통과해야만 dev에 들어간다.

훅은 저장소 전체 설정(`core.hooksPath`)으로 걸리기 때문에 **모든 워크트리에서 실행된다.**
그래서 각 모드의 첫 줄이 "지금 브랜치가 dev인가"를 확인하고, 아니면 즉시 통과시킨다. 워커가
워크트리에서 무슨 커밋을 해도 아무 일이 없는 이유가 이 한 줄이다.

## 가장 위험한 실수: fast-forward 머지

훅은 **머지 커밋**에 걸려 있다. 그런데 합칠 내용이 일직선으로 이어져 있으면 git은 머지 커밋을
만들지 않고 브랜치 포인터만 앞으로 옮긴다.

```
정상   dev ●──●─────────◉      ← 머지 커밋이 생긴다. 훅은 여기에 걸린다
              ╰──○──○──╯

위험   dev ●──●──○──○          ← 머지 커밋이 없다. 포인터만 이동한다
                      ▲          훅이 걸릴 자리가 없어 게이트가 사라진다
```

이렇게 되면 검사도 안 하고, 보고서도 안 생기고, 그런데 dev는 이미 전진해 있다. 실패로 보이지
않고 조용한 성공처럼 보이기 때문에 가장 위험하다.

그래서 세 곳에서 막는다. dev 워크트리에 `merge.ff=false` 를 걸고, `ticket.sh merge` 가
`--no-ff` 를 항상 붙이고, `--selftest` 가 그 설정이 살아 있는지 확인한다.

알아채는 방법은 간단하다. 머지했는데 그 티켓 폴더에 파일이 하나도 안 생겼으면 이 상황이다.

## 정리하면

1. 판정하는 곳은 `verify.sh` 하나뿐이고, 리뷰 에이전트는 지적만 할 수 있다.
2. `.tickets/queue.md` 에 올라온 것은 검사를 통과해서 머지된 것이다. 실패한 것은 여기 없다.
3. dev에 머지가 들어오면 보고서가 생긴다. 훅이 자동으로 머지했든 사람이 충돌을 해결했든 같다.

# 설치

## 전제 두 가지

- **`dev` 가 별도 git 워크트리로 체크아웃돼 있어야 한다.** 워크트리끼리 로컬 머지하는 방식이라
  이건 선택이 아니다.
- Orca 런타임이 돌고 있고, Settings > Experimental 에서 orchestration 이 켜져 있어야 한다.

## 세 번째 인자를 먼저 확인한다

이걸 틀리면 첫 발사가 조용히 실패한다.

```sh
orca repo list --json | jq -r '.result.repos[].displayName'
```

출력에 있는 이름을 그대로 쓴다. 이건 Orca에 등록된 저장소의 `displayName` 이고, 워크트리 이름도
브랜치 이름도 아니다. 저장소 루트와 dev 워크트리가 같은 부모 폴더에 나란히 있어서
(`myapp/`, `myapp-dev/`) 워크트리 이름을 넣기 쉽다.

```sh
sh install.sh <저장소루트> <dev워크트리> <Orca저장소이름>
# 예: sh install.sh ~/proj/myapp ~/proj/myapp-dev myapp
```

`install.sh` 가 이 이름을 `orca repo list` 와 대조해서 없으면 후보 목록을 찍고 멈춘다. Orca
런타임이 꺼져 있으면 검증을 못 하므로, 그때 나는 증상을 적어둔다.

> `ticket.sh new` 가 아무 출력 없이 종료된다. `orca worktree create` 가 `repo_not_found` 를
> 돌려주는데 orca는 실패도 종료 코드 0으로 내보내기 때문에, `set -eu` 아래에서 그 다음 `jq` 가
> 빈 값을 만나 죽는다. `sh -x .githooks/ticket.sh new ...` 로 트레이스하면 JSON이 보인다.
> `ticket.sh` 상단의 `REPO=name:<이름>` 을 위 목록의 이름으로 바꾼다.
>
> (지금 버전은 응답의 `.ok` 를 검사해서 에러 코드와 확인 명령을 찍는다. 조용히 죽는 건 옛 버전이다)

## 설치 직후 `verify.sh` 를 교체한다

기본 `verify.sh` 는 아직 설정되지 않았다는 이유로 머지를 막는다. 첫 티켓을 발사하기 전에
이 프로젝트의 검사 명령으로 바꿔야 한다.

```sh
# 워크트리 루트가 현재 디렉터리다. 검사 대상이 하위 폴더면 서브셸로 내려간다
(cd crawler && uv run pytest -q)
```

바꾼 뒤에는 dev 워크트리에서 직접 한 번 돌려서 종료 코드 0을 눈으로 확인한다.

```sh
cd <dev워크트리> && sh ../.githooks/verify.sh; echo "exit=$?"
```

이걸 안 하면 첫 머지가 게이트에서 막히고, 원인이 워커 코드인지 게이트 설정인지 구분하는 데
라운드를 쓴다. 실제로 겪은 실패가 두 가지 있다. 루트에 없는 `node_modules` 를 루트에서 확인해서
첫 줄에서 죽은 경우, 그리고 테스트가 `crawler/` 에 있는데 루트에서 `uv run pytest` 를 돌려
`Failed to spawn: pytest` 가 난 경우다.

**넣을 검사를 고르는 기준은 하나다. 지금 에러가 0인 도구만 넣는다.** 이미 실패하고 있는 검사를
넣으면 게이트가 항상 막는 상태가 되고, 그러면 사람이 `--no-verify` 로 우회하기 시작한다. 우회가
습관이 되면 게이트가 있으나 없으나 마찬가지다.

## 남은 수동 작업

`install.sh` 가 끝에 출력하지만 스크립트가 대신 할 수 없는 것이 하나 더 있다. 워크트리 **상위**
`CLAUDE.md` 에 `templates/CLAUDE-workflow-section.md` 내용을 붙이는 일이다. Orca 설정 화면에만
넣어두면 워커가 읽지 못하고, 그러면 아무도 `[done]` 을 붙이지 않아서 dev 세션이 계속 기다린다.

## 전역 스킬 둘은 따로 건다

`writing-session-worklogs`(세션 기록)와 `building-project-llm-wiki`(프로젝트 문서를 LLM 위키로 세우기)는
이 워크플로 전용이 아니라 **아무 프로젝트에서나 쓰는 스킬**이다. 그래서 프로젝트마다 복사하지 않고 전역에
한 번만 건다 — 두 벌이 되면 갈린다.

```sh
ln -s "$(pwd)/skills/writing-session-worklogs" ~/.claude/skills/writing-session-worklogs
ln -s "$(pwd)/skills/building-project-llm-wiki" ~/.claude/skills/building-project-llm-wiki
```

`install.sh` 는 이 두 스킬을 건너뛴다(`건너뜀(전역 스킬)`). 수정은 이 레포의 파일 하나에서만 한다.

# 한 티켓 돌리기

```sh
cp templates/spec.html /tmp/t.html      # 5슬롯을 채운다. 초안은 사람이 쓴다
                                        # dev 세션에서 /writing-ticket-specs 로 빈 슬롯을 점검한다
cd <dev워크트리>
.githooks/ticket.sh new fix/foo /tmp/t.html
#   브랜치명이 정규화된다(fix/foo → fix-foo). 발사 출력의 '실제 브랜치'를 이후 명령에 쓴다

.githooks/ticket.sh wait
#   빈손으로 돌아오는 것은 실패가 아니라 체크포인트다. 다시 wait 한다
#   두 번 연속 빈손이면 워커가 멈춘 것이다. git log -1 <브랜치> 로 확인하고 send 로 지시를 다시 보낸다
#   질문 통지가 오면 답도 send 로 보낸다 (orca orchestration reply 는 턴이 끝난 워커를 못 깨운다)

.githooks/ticket.sh merge fix-foo       # ★ 판정 + 보고서. [done] 통지면 승인 없이 즉시
#   .tickets/queue.md 마지막 줄 → review-<sha>.html 를 읽고 사람에게 요약한다
#   요약은 /writing-korean-explainers 규칙으로: 결론 첫 줄 → 기능 영향 있음/없음 → 마지막에 선택지
#   보고서를 그대로 붙여넣지 마라. 요약을 사람이 다시 하게 된다

.githooks/ticket.sh send fix-foo /tmp/rework.md   # 재요청. 같은 워크트리를 쓴다
.githooks/ticket.sh close fix-foo                 # 워크트리 제거 + 라운드 리뷰를 review.html 로 종합
#   close 뒤 /writing-session-worklogs 로 과정을 docs/worklog/ 에 한 장 남긴다 — 보고서는 결과, 이쪽은 과정이다
```

산출물은 티켓 폴더 하나에 모인다.

```
.tickets/
├─ queue.md                통과해서 머지된 것만 한 줄씩
│                          형식: - [브랜치](링크) 시각 — <spec.html 의 h1>
└─ <티켓>/
   ├─ spec.html            사람이 쓴 지시서. 워커의 유일한 입력이다
   ├─ diagram.html         (선택) 흐름이 복잡할 때만. /archify 로 그려 spec 에서 링크한다
   ├─ verify-<sha>.log     검사 결과. 시도마다 따로 쌓여서 덮이지 않는다
   ├─ review-<sha>.html    머지 한 번당 보고서 한 장. 브라우저에서 연다
   ├─ review.html          close 때 라운드 보고서들을 합친 최종본. 확인 항목은 체크박스다
   └─ rounds/              합쳐진 뒤 옮겨진 라운드 원본
```

보고서는 스펙과 같은 HTML 한 장이다. 훅이 머리(제목·스타일)와 `기계 검증` 블록까지 쓴 파일에
리뷰 에이전트의 출력이 `<section>` 조각으로 이어붙는다. 왼쪽에 파란 줄이 그어진 `기계 검증`
블록은 LLM이 건드리지 못한다 — 둘을 섞어놓으면 LLM의 의견이 기계가 확인한 사실처럼 읽힌다.

읽는 순서는 항상 같다. `queue.md` 의 마지막 줄을 보고, 거기 링크된 보고서를 읽고, 실패한
경우에만 검사 로그를 연다. `close` 된 티켓은 `review.html` 하나만 읽는다.

# 더 알아볼 만한 것

- **`verify.sh` 에 무엇을 넣을지** — 문구나 설정만 바꾸는 티켓은 타입 검사에 걸리지 않는다.
  이런 티켓을 어떻게 검사 대상으로 만드는지가 게이트의 실효를 결정한다.
- **지시서 다섯 칸 채우기** — 다시 시키게 되는 원인은 대개 워커의 실수가 아니라 지시서의
  빈칸이다. 판정 기준은 `writing-ticket-specs` 스킬에 있다.
- **완료 통지가 유실되는 경로** — 워커가 질문을 보냈는데 답이 전달되지 않는 사고가 이 계열에서
  가장 자주 난다. 아래 함정 14~17번.
- **티켓을 두 개 동시에 돌릴 때** — 보고서가 엉뚱한 diff를 보게 되는 조건과 그걸 막는 락.
  아래 함정 7·13번.
- **다른 저장소로 옮길 때** — 통합 브랜치 이름이 `dev` 가 아니거나 PR 기반으로 일하는 팀에서는
  무엇이 먼저 깨지는지.

# 참고 자료

여기부터는 처음 읽을 필요가 없다. 막혔을 때 찾는 자료다.

## 어느 상황에서 무엇이 남는가

| 상황 | 남는 것 | 다음에 할 일 |
|---|---|---|
| **정상** | 검사 로그(통과) · 보고서 · 큐 한 줄 · dev 전진 | 보고서를 요약해서 사람에게. 재요청 또는 `close` |
| **게이트 실패** | 검사 로그(실패)만. 보고서·큐 없음. dev 무변화 | 로그를 읽고 `send <브랜치> <재요청파일>`. 새 워크트리를 만들지 않는다 |
| **충돌 → 사람이 해결 → 통과** | 정상과 동일 | 정상과 동일. 해결분도 게이트를 통과했다 |
| **충돌 → 해결했는데 검사 실패** | 검사 로그(실패). 머지는 진행 중 상태로 남는다 | 더 고쳐서 다시 `git commit`, 또는 `git merge --abort` |
| **fast-forward 우회** | 아무것도 없는데 dev는 전진 | 가장 위험하다. 위 설명 참조 |
| **통지가 `Failed:` 또는 `[done]` 없음** | — (머지하지 않는다) | 이유를 사람에게 보고하고 `send` 로 지시를 다시 보낸다 |
| **워커가 질문했다** | — | 답도 `send` 로 보낸다. `orca orchestration reply` 는 턴이 끝난 워커를 못 깨운다 |
| **dev에 직접 커밋 (문서·설정)** | 아무것도 없음 | 의도된 동작이다. dev 직접 커밋은 사소한 변경만 오는 자리다 |
| **워크트리에서 커밋** | 아무것도 없음 | `[done]` 은 dev 세션에게 보내는 표식일 뿐이다 |
| **재요청 후 두 번째 머지** | 검사 로그가 sha별로 하나 더 | 1차 실패 로그가 덮이지 않는다 |
| **리뷰 에이전트 실패** | 검사 로그(통과) · 보고서는 기계 블록만 · 큐 없음 · dev 전진 | 큐에 없다고 머지 안 됐다고 읽지 말 것 |
| **동시에 두 머지** | 보고서 작성이 `.tickets/.lock` 으로 직렬화된다 | 300초 넘으면 죽은 락으로 보고 강제 해제한다 |
| **머지 대상 브랜치를 못 알아냄** | 산출물이 `_dev/` 로 떨어진다 | 파이프라인은 멈추지 않는다. 라벨은 폴더 이름일 뿐이다 |
| **`verify.sh` 가 없거나 실행권한 없음** | 게이트를 통과로 처리하고, 보고서에 그 사실을 적는다 | 전부 갖춘 뒤 켜려 하면 시작을 못 한다는 판단이다 |

## 막혔을 때

| 증상 | 명령 |
|---|---|
| 게이트 실패로 머지가 취소됐다 | `cat .tickets/<slug>/verify-<sha>.log` → `ticket.sh send <브랜치> <재요청파일>` |
| `merge` 가 머지를 시작하지 못했다고 한다 | 게이트 실패가 아니다(검사 로그가 없다). `git -C <dev> merge --abort`, `git branch --list` |
| `send` 가 에이전트 터미널이 없다고 한다 | 워크트리가 이미 `close` 됐거나 브랜치명이 다르다. `orca terminal list --json \| jq -r '.result.terminals[].branch'` |
| 충돌 상태에서 그만두고 싶다 | `git merge --abort` |
| 훅이 도는지 자체가 의심된다 | 훅 파일을 `exit 1` 로 바꿔보고 머지를 시도한다 |
| 설치 상태를 점검하고 싶다 | dev 워크트리 안에서 `sh .githooks/dev-sync.sh --selftest` |
| 락이 남아서 막힌다 | `rm -rf .tickets/.lock` |
| 워크트리가 dev보다 낡았다 | `git -C <워크트리> merge dev` (자동 전파는 없다) |
| `close` 의 종합이 실패했다 | `sh .githooks/dev-sync.sh consolidate <브랜치>` |

## git 훅 함정 — 측정으로 확인한 것들

문서에 안 적혀 있고, 모르면 게이트가 조용히 통과한다.

| # | 사실 | 대응 |
|---|---|---|
| 1 | `pre-merge-commit` 시점엔 `MERGE_HEAD`·`MERGE_MSG` 가 아직 없다 (git이 커밋할 때 쓴다) | 무엇을 머지하는지는 환경변수 `GITHEAD_<sha>=<브랜치>` 에서 읽는다. `MERGE_HEAD` 는 충돌 경로 폴백으로만 |
| 2 | `git merge` 는 `post-commit` 을 안 띄운다 (`post-merge` 만) | 머지 후 처리를 `post-commit` 에만 두면 수동 머지가 보고서 밖으로 빠진다 |
| 3 | 충돌 후 사람이 `git commit` 으로 마치면 `pre-merge-commit`·`post-merge` 둘 다 안 뜨고 `pre-commit`/`post-commit` 이 뜬다 | 그래서 훅이 2개가 아니라 4개 필요하다 |
| 4 | fast-forward 머지는 `pre-merge-commit` 을 건너뛴다 | dev 워크트리에 `merge.ff=false`. `ticket.sh merge` 도 `--no-ff` 고정 |
| 5 | 훅 안에서 `GIT_DIR`·`GIT_INDEX_FILE` 등이 방금 커밋한 워크트리를 가리킨다 | 훅 첫머리에서 `unset` — 안 하면 `git -C 다른워크트리 status` 가 clean을 dirty로 오판한다 |
| 6 | 훅은 로그인 셸이 아니라 PATH가 최소다 | `verify.sh` 가 PATH를 직접 얹고, `CLAUDE_BIN` 은 절대경로. 재현: `env -i PATH=/usr/bin:/bin sh verify.sh` |
| 7 | macOS에 `flock` 이 없다 | `mkdir` 원자성으로 락을 잡는다 (300초 초과 시 강제 해제) |
| 8 | `--allowedTools` 는 가변인자라 뒤의 positional(프롬프트)까지 삼킨다 | 프롬프트를 먼저, `--allowedTools` 를 맨 뒤에 |
| 9 | Orca가 브랜치 이름을 정규화한다 (`fix/x` → `fix-x`) | 훅이 브랜치 이름 규칙에 의존하지 않게 만든다 — 이 스캐폴드는 "지금 브랜치가 dev인가"만 본다. rename 하면 orca의 `branch:` 조회가 깨지므로 rename도 하지 않는다 |
| 10 | `orca terminal list --worktree branch:<브랜치>` 가 어떤 형태로도 0건을 준다. 같은 셀렉터가 `worktree rm` 에서는 동작한다 | 필터 없이 전체를 받아 `.branch` 로 고른다. `ticket.sh handle_of` 가 그렇게 한다 |
| 11 | 터미널 레코드에 `agentType` 필드가 없다 | 에이전트 터미널은 `title` 이 `✳` 로 시작하는 쪽이다. 더 확실한 건 발사 때 받은 핸들을 `.tickets/<slug>/terminal` 에 적어두고 그걸 쓰는 것 |
| 12 | `terminal send`(TUI 타이핑)로 여러 줄 재요청을 보내면 빈 줄에서 조기 전송돼 앞부분만 들어간다. `worker_done` 규칙도 다시 주입되지 않는다 | 재요청도 발사와 같은 경로를 쓴다: `task-create` → `dispatch --inject`. `ticket.sh send` 가 파일과 텍스트를 모두 받는다 |
| 13 | dev 워크트리는 티켓들이 공유한다 — 다른 머지가 진행 중이면 `git merge` 가 `MERGE_HEAD exists` 로 즉시 거부한다 | 게이트 실패와 구분해야 한다. `merge` 가 선검사하고, 게이트 실패는 검사 로그가 있을 때만 주장한다 |
| 14 | `orca orchestration reply` 는 메시지를 저장만 한다 — 턴이 끝난 워커를 깨우지 않는다. `worker_done` 을 보낸 워커는 대기 중이 아니라 턴이 끝난 상태다 | 워커에게 가는 말은 재요청이든 질문 답변이든 전부 `ticket.sh send` 다. `reply` 는 쓰지 않는다 |
| 15 | 워커 질문(`decision_gate`)이 `worker_done` 뒤에 도착할 수 있다(도착 순서 역전) | `wait` 가 `worker_done,escalation,decision_gate` 를 모두 받는다. 질문이 섞여 오면 `wait` 가 "답은 send 로" 를 찍는다 |
| 16 | `orchestration check` 를 `--terminal` 없이 부르면 어떤 메일박스도 열리지 않고 항상 `count:0` 이다(에러도 안 낸다). 통지는 하네스가 턴 경계에 주입하는 경로로만 보여서, 사람이 ESC를 눌러 턴을 끊을 때까지 dev가 안 깨어난다 | `wait` 가 `self_handle()` 로 자기 핸들을 명시한다. `ORCA_PANE_KEY="<tabId>:<leafId>"` 를 `terminal list` 레코드와 매칭해 얻는다. 못 찾으면 에러로 죽인다 — 조용히 빈손을 돌리면 "워커가 아직 작업 중"으로 오독된다 |
| 17 | 하네스 주입 경로는 메시지를 읽음 처리하지 않는다 → 옛 라운드 `worker_done` 이 미읽음으로 쌓이고, `wait` 가 그것을 즉시 물어와 아직 돌고 있는 워커를 두고 merge로 넘어간다 | `new`·`send` 가 dispatch 직전에 `drain_notices()` 로 미읽음을 비운다 |
| 18 | `orca` 는 실패 시 exit 1 + `{"ok":false}` 를 stdout으로 낸다. `set -e` 아래 `X=$(orca ...)` 는 출력 한 줄 없이 죽고, `orca ... \| jq -r ...` 는 파이프라인 종료 코드가 `jq` 것이라 실패가 사라지고 값만 `"null"` 이 된다 | `orca_ok()` 하나로 감싼다. `\|\| true` 로 받아 `.ok` 를 판정하고, 진단은 stderr로, 값 추출용 `jq` 는 다음 줄에서 따로 돌린다. stderr를 병합하지 않는 이유는 `check --wait` 의 keepalive가 JSON을 깨뜨리기 때문이다 |
| 19 | `terminal wait --for tui-idle` 도 타임아웃 시 `{"ok":false}` + exit 1 이다 — 그 시점에 워크트리는 이미 만들어져 있다 | `orca_ok` 가 그 사실을 찍는다. `close` 는 `worktree rm` 실패를 삼키고 `review.html` 종합까지 간다 |

디버깅할 때는 "훅이 안 돈다"와 "훅은 돌지만 조건이 안 맞다"를 먼저 갈라야 한다. 훅 파일을
`exit 1` 로 바꿔서 실제 실행 여부를 확인하는 것이 가장 빠르다.

## 설계 근거

**선언은 LLM이, 판정은 기계가 한다.** LLM은 자기가 작업을 마쳤다는 것은 알지만 그게 안전한지는
모른다. 그래서 커밋 마커가 `[ready]`(예측)가 아니라 `[done]`(사실 선언)이고, 머지 가부는 프로세스
종료 코드가 정한다.

**트리거는 dev 머지 시점 하나다.** feature 커밋을 트리거로 쓰면 브랜치 이름 규칙과 마커 유실에
의존하게 되고, 검사 대상이 머지 전 브랜치라서 머지 후 깨지는 충돌을 못 잡는다.

**리뷰는 게이트가 아니다.** 게이트가 두 개면 리뷰가 도는 동안 머지가 밀리고, LLM 의견이 사실상
게이트처럼 굳는다. 리뷰의 목적은 승인 도장이 아니라 읽을 범위를 줄이는 것이다. 7개 파일을 안
읽게 하는 게 아니라 18줄로 좁혀서 읽게 한다.

**기계층과 판단층을 분리한다.** 보고서의 `기계 검증` 블록은 훅이 쓰고 LLM은 건드리지 못한다.
섞이면 의견이 사실의 신뢰도를 빌려간다.

**게이트에 넣을 도구는 기존 에러가 0이어야 한다.** 지금 실패 중인 검사를 넣으면 게이트가
차단기가 되고 곧 `--no-verify` 우회를 부른다. 우회가 습관이 되면 게이트는 없는 것과 같다.

## 이 스캐폴드에 없는 것

- **PR과 원격 CI 연동** — 이 워크플로는 로컬 워크트리 머지 기반이다. `main` 은 push용이다.
- **위험도 등급과 큐 우선순위** — 근거가 쌓이기 전에는 만들지 않는다.
- **재처리나 삭제 같은 복구 수단** — 재요청(`send`)이 그 역할을 한다.
