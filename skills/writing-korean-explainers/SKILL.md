# 한국어 설명문 쓰기

## 목표

읽는 사람이 **3분 안에 읽고, 머릿속에 구조 하나를 남기는** 것. 완전한 명세가 아니다.
다 못 담은 것은 마지막 "더 알아볼 만한 것"으로 넘긴다.

## 골격 (이 순서를 지킨다)

위에서 아래로 내려가되, **각 층이 앞 층의 이유를 설명하는** 순서다.

1. **전체 구조** — 무엇이 몇 개 있고 어디로 모이는가. 도해 1개.
2. **역할 분담** — 누가 무엇을 하고, **무엇을 할 수 없는가**. 못 하는 일이 설계의 핵심인 경우가 많다.
3. **순서** — 실제로 일어나는 일을 번호대로. 도해 1개.
4. **왜 이렇게 생겼나** — 구조가 이상해 보이는 지점 한두 개만 골라 해명한다.
5. **가장 위험한 실수** — 실패로 안 보이는 실패가 있으면 반드시 넣는다. 알아채는 방법까지.
6. **정리하면** — 3줄. 앞에 안 나온 내용은 넣지 않는다.
7. **더 알아볼 만한 것** — 4~5줄. 각 줄에 "왜 볼 만한지"를 붙인다.

3·4·5는 대상에 따라 합치거나 뺀다. 1·2·6·7은 빼지 않는다.

## 분량

본문 2,000자 안쪽. 도해와 표는 읽는 속도가 빠르므로 이 계산에서 뺀다.
넘으면 **문장을 줄이지 말고 항목을 버린다.** 짧아진 설명 열 개보다 온전한 설명 다섯 개가 낫다.

## 규모가 작은 보고

설명문 한 장과 한 번의 보고는 규모가 다르다. 위 골격을 짧은 보고에 그대로 적용하면
머지 한 건을 놓고 7단계 문서가 나온다.

| 상황 | 분량 | 적용 범위 |
|---|---|---|
| 시스템·구조·조사 결과 설명 | 본문 2,000자 | 골격 전부 |
| 작업 한 건 보고, 실패 보고, 완료 통지 정리 | 5~10줄 | 아래 세 가지 + 한국어 문장 규칙 |

**하나 — 결론을 첫 줄에 쓴다.** 통과했는지 막혔는지를 먼저 말하고, 경위는 그 다음이다.

**둘 — 사람이 판단할 것만 남긴다.** 기계가 이미 판정한 것은 한 줄로 접는다.
검사 결과를 다시 설명하는 문장은 지운다.

**셋 — 마지막 줄은 선택지다.** 다음에 할 수 있는 일을 두 개로 좁혀 제시한다.
선택지가 없으면 보고를 받은 사람이 무엇을 해야 하는지 다시 물어야 한다.

이 규모에서는 도해와 "더 알아볼 만한 것"을 넣지 않는다.

## 추상화 강도 — 낮게

**실제 이름을 쓴다.** `dev 브랜치`, `머지 커밋`, `verify.sh`, 훅 이름.

비유는 처음 개념을 꺼낼 때 한 문장까지만 쓰고 바로 실제 이름으로 돌아온다.
비유로 만든 어휘를 문서 전체의 공용어로 만들면 안 된다 — 읽는 사람이 실제 이름과
비유 이름을 동시에 외워야 하고, 그러면 이해가 오히려 늦어진다.

| 이렇게 쓰지 마라 | 이렇게 쓴다 |
|---|---|
| 검문소가 짐을 검사한다 | `pre-merge-commit` 훅이 `verify.sh` 를 실행한다 |
| 감지기는 매듭에 달려 있다 | 훅은 머지 커밋이 만들어질 때 실행된다 |
| 담 안에서는 아무 일도 안 일어난다 | 워크트리 안에서 하는 커밋은 훅을 실행하지 않는다 |

## 자연스러운 한국어

영어 직역체는 스스로 알아채기 어렵다. 아래 네 가지만 확인한다.

**하나 — 명사로 끝내지 말고 동사로 끝낸다.**
`판정 없음` → `판정하지 않는다` / `게이트 우회` → `게이트를 우회한다`

**둘 — 문장을 접속사로 잇는다.** 격언처럼 끊어 놓으면 연결을 읽는 사람이 직접 해야 한다.
`그래서 · 반면 · 이때 · 그런데 · 덕분에` 를 아끼지 않는다.

**셋 — 소제목과 도입부를 문장으로 쓴다.**
`급소 둘` → `여기서 두 가지를 짚어둘 만하다`
`이 구조가 지켜주는 세 가지` → `정리하면`
`밑에 깔린 문장 하나` → 그냥 그 문장을 쓴다

**넷 — `~것이 ~이다` 구문을 줄인다.**
`각자 못 하는 일이 이 설계의 실질이다` → `역할을 이렇게 나눈 이유가 있다`

문체는 평서체 `~한다`. 존댓말도 격언체도 쓰지 않는다.

## 도해

**2~3개.** 넘으면 그림이 아니라 목록이 된다.

- 코드 펜스 안에 ASCII 로 그린다. 라벨은 **실제 이름**으로 붙인다.
- 흐름은 위에서 아래, 갈라지는 곳은 `┌─┴─┐` 로 두 갈래까지만.
- 그림 오른쪽에 짧은 주석을 붙여 "이게 왜 여기 있나"를 답한다.
- 그림에 넣은 내용은 아래 산문에서 반복하지 않는다. 대신 **그림에서 안 보이는 이유**를 쓴다.

## 영문과 코드

지우는 게 기본이지만, **정확도가 걸리면 남긴다.**

- 남긴다: 파일명, 함수명, 명령, 설정 키, 브랜치명 — 사용자가 실제로 검색하거나 입력할 것
- 지운다: 설명을 위해 만든 영어 용어(shim, fail closed, handoff), 인용할 필요 없는 코드 조각
- 코드 블록은 **파일 구조와 도해에만** 쓴다. 로직을 인용할 거면 한 줄로 줄인다.

## 표

같은 축으로 비교되는 항목이 3개 이상일 때만 쓴다. 2개면 문장이 빠르다.
`역할 / 하는 일 / 할 수 없는 일` 처럼 마지막 열에 부정형을 두면 정보량이 크게 늘어난다.

## 흔한 실패

- **완전하게 쓰려다 길어진다** → 버린 것을 "더 알아볼 만한 것"에 한 줄로 남기면 죄책감 없이 버릴 수 있다
- **비유를 끝까지 끌고 간다** → 두 번째 문단부터는 실제 이름으로 돌아왔는지 확인한다
- **표를 세 개 이상 쓴다** → 표가 많으면 산문이 사라지고 이유가 안 남는다
- **정리 블록에 새 내용을 넣는다** → 정리는 앞에서 이미 말한 것만 압축한다
- **위험한 실수를 뺀다** → 조용히 실패하는 경로가 있으면 그것이 이 문서의 가장 큰 값이다

## 마무리 블록

```markdown
# 더 알아볼 만한 것

- **<주제>** — <왜 볼 만한지 한 줄. 어디가 아픈지, 무엇이 갈리는지>
```

주제는 4~5개. 문서에서 일부러 뺀 것, 프로젝트마다 달라지는 것, 사고가 자주 나는 곳에서 고른다.
