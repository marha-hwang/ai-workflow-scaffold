# 묶음 작업 계획

큰 작업은 하위 티켓으로 쪼개기 전에 **구조를 먼저 정한다.** 순서는 목표 → 사실 조사 → 테스트 시나리오 → 결정 → 분할 → 순서 → 산출물이다. 하위 티켓 스펙은 이 구조 위에서 사람이 쓰고, 실행은 `ticket-hub`가 한다.

## 계획의 모양 (이 순서로 전부 채운다)

1. **목표와 외부 약속.** 끝났을 때 무엇을 시연·확인하나. 날짜가 걸린 외부 약속(제출일·보고일)과 그때 통과해 있어야 할 것 하나. 이번에 뺀 것
2. **사실 조사.** 이미 있는 것과 새로 만들 것, **두 티켓이 같은 파일을 고치게 될 자리(핫스팟)**. 코드를 직접 보고 적는다. 사람에게 묻지 않는다. 핫스팟은 폴더가 아니라 **파일 목록**으로 적는다. 경로 등록표·주 메뉴·라우터 마운트처럼 "새 화면·API마다 한 줄씩 붙는 파일"은 폴더가 갈려도 모든 티켓이 만나는 자리라 빠뜨리기 쉽다(2026-10-01: 소유표에 없던 경로 등록 파일을 거의 모든 티켓이 고쳤다)
3. **테스트 시나리오.** 기능 묶음마다 `# · 상황 · 기대 결과` 표. 기대 결과를 모르는 칸은 `미정:`으로 남긴다. 이 미정 칸이 곧 결정 목록이다
4. **결정.** 미정 칸을 한 번에 모아 묻는다(권장안을 앞에). 특정 하위 티켓에만 걸린 칸은 "그 스펙 전까지"로 미뤄도 된다
5. **분할.** 기준은 **파일 소유권**이다. 핫스팟마다 그 파일을 고치는 티켓을 하나로 정하고, 공통 부품은 전담 티켓 하나가 고친다. migration을 쓰는 티켓을 명시한다. 화면을 맞추는 작업은 기준선(현재와 목표의 차이 목록) 티켓 뒤에 둔다. 여기서 두 가지를 같이 정한다:
   - **번호 대역.** migration 버전·ADR 번호처럼 순번을 쓰는 파일은 티켓마다 대역을 미리 나눠 스펙에 적는다(예: 티켓마다 날짜 하루). 파일 이름이 달라 git 충돌로 안 잡히고, 같은 번호 둘이 함께 머지된다. 게이트(`verify.sh`)의 번호 겹침 검사는 그 뒤의 안전망이다
   - **공용 문서.** 작업 로그·위키·해시 대장·추적표·계획 진행 기록처럼 모든 티켓이 끝에 줄을 붙이는 문서는 어느 티켓의 소유도 아니다. 워커는 고치지 않고 `[done]` 커밋 본문 `문서 반영:`에 적고, close 때 허브가 반영한다. 목록을 계획 문서에 적어 스펙 "손대지 말 것"에 그대로 들어가게 한다
   - **티켓 크기 — 토큰과 작업 시간을 기준으로.** 티켓 하나마다 고정비가 붙는다: 세션 기동, 지침·스펙 읽기, 코드 탐색, 게이트(`verify.sh`), 리뷰 에이전트, 사람 리뷰, 머지·close. 이 고정비보다 작은 일은 따로 떼지 않고, **같은 파일·모듈을 읽거나 고치는 이웃 티켓에 합친다.** 같은 코드를 두 세션이 각자 읽으면 토큰이 두 번 들고 리뷰도 두 번 한다. 반대로 맡는 파일이 너무 많아 탐색만으로 세션 컨텍스트가 차는 크기면 나눈다. 티켓 수는 결과로 나오는 숫자다. 동시 실행 상한(기본 3~4)보다 훨씬 많이 잘게 쪼개도 빨라지지 않고 대기열만 길어진다
6. **순서.** 의존 그래프 → 묶음. 다음 묶음으로 가는 조건은 날짜가 아니라 **앞 티켓의 시나리오 시험 통과 + staging 확인**이다. 가장 긴 의존 경로를 적고 그 첫 티켓 스펙을 먼저 쓰게 한다. 전체 작업 시간은 이 경로의 길이가 정한다. 그래서 **경로 위의 티켓은 작게 잘라 빨리 끝나게 하고, 경로 밖의 티켓은 합쳐서 크게** 만든다. 소비 티켓이 앞 티켓의 구현이 아니라 형태(API 응답·타입)만 필요하면, 그 형태를 계획 문서에 먼저 적고 의존을 끊는다. 형태가 담긴 파일의 소유는 여전히 한 티켓이다
7. **진행 규칙.** 구현 일수로 일정을 잡지 않는다(워커 병렬로 줄어든다). 속도를 정하는 것은 사람 쪽 일(스펙·결정·리뷰)과 외부 대기다. 동시 실행 수 = 리뷰 보고서를 판단할 수 있는 수(기본 3~4). 돈·상태가 걸린 티켓은 깊게 리뷰한다고 표시한다
8. **산출물.** 레포의 계획 문서 하나(범위·결정·시나리오·티켓 표·충돌 규칙·다음 과업 후보와 그 전제)와 `.tickets/bundles/<묶음>/plan.tsv`. `plan.tsv`는 `ticket.sh`가 읽는 형식 그대로 쓴다:

```
# 묶음 pivot. 출처: docs/…/plan/<계획>.md      ← '#' 줄은 주석. 머리 줄(열 이름)은 쓰지 않는다
T1	pivot-t1-bank-transfer	-	계좌이체 서버
T6	pivot-t6-ui-tokens	T2	공통 토큰·부품
T8	pivot-t8-booking-detail	T1,T6	거래 상세
```

열은 탭으로 나눈 넷: `id · 브랜치 · 의존 · 제목`. 브랜치는 `/` 없이 묶음 약칭을 앞에 붙인다. 의존은 같은 파일 안의 id를 쉼표로, 없으면 `-`. **아직 정해지지 않은 티켓(예: 기준선 결과로 나눌 화면 티켓)은 행을 만들지 않고 의존에도 쓰지 않는다** — 없는 id를 의존에 쓰면 그 티켓은 영원히 발사되지 않는다. 정해지면 행을 추가하고 의존을 고친다. 스펙 자리는 `.tickets/bundles/<묶음>/<브랜치>/spec.html`이다

티켓 표의 열은 고정이다: `묶음 | 티켓 | 하는 일 | 완료 기준(시나리오 ID) | 맡는 파일 | 의존`. 완료 기준 칸이 시나리오 ID가 아니면 아직 3번이 덜 된 것이다.

충돌 규칙(공통 부품은 누가, 핫스팟은 누가, migration은 누가, 번호 대역, 공용 문서 목록)은 각 하위 티켓 스펙의 "손대지 말 것"·"실행환경·제약"에 그대로 들어갈 문장으로 쓴다.

## 하위 티켓 스펙은 쓰지 않는다

스펙 초안은 사람이 쓴다(`writing-ticket-specs`). 계획을 마치면 "어느 티켓 스펙부터 쓰면 되는지"까지만 말한다. **"초안을 써 드릴까요"라고 제안하지도 않는다.** 대신 쓰면 계획을 이해하지 못한 채 발사된다. 사람이 "네가 채워"라고 하면 그때만 채우고 `(추정)`을 붙인다.

## 자주 틀리는 곳

| 실수 | 고칠 것 |
|---|---|
| 조사 없이 "화면 묶음 A(약 4개)"처럼 쪼갠다 | 기준선 티켓으로 차이 목록을 먼저 만들고 그 뒤에 쪼갠다 |
| 계약·스키마를 한 티켓에 몰아 모두가 그 뒤에 선다 | 핫스팟만 소유 티켓으로 묶고 나머지는 1묶음에서 바로 병렬로 |
| 날짜별 일정과 "하루 안에 머지" 가정 | 날짜는 외부 약속 체크포인트 하나만. 나머지는 의존과 전환 조건 |
| 시간이 모자라면 무엇을 뺄지만 적는다 | 미룬 것은 "다음 과업 후보"에 전제(필요한 결정·외부 준비물)와 함께 |
| 계획을 대화에만 남긴다 | 계획 문서 + `plan.tsv`를 남겨야 허브가 발사한다 |
| 핫스팟을 폴더로만 센다 | 경로 등록표·메뉴·라우터처럼 한 줄씩 붙는 파일을 따로 찾아 소유 티켓을 정한다 |
| 번호를 워커가 고르게 둔다 | migration·ADR 번호 대역을 티켓마다 스펙에 적는다 |
| 일의 단위마다 티켓을 하나씩 만든다 | 같은 파일을 읽는 작은 일은 한 티켓으로 합친다. 고정비(기동·탐색·게이트·리뷰)는 티켓 수만큼 든다 |
| 형태만 필요한데 구현 완료를 의존으로 건다 | 형태를 계획 문서에 먼저 적고 의존을 끊어 가장 긴 경로를 줄인다 |
