# 티켓 허브

허브는 **사람과 이야기하는 유일한 세션**이다. 티켓마다 따로 뜬 티켓 dev 세션이 발사·대기·요약을 하고, 허브는 발사·**머지**·현황·결정 전달·close 때 문서 반영을 한다.

머지를 허브 한 곳에 모으는 이유: dev 작업 트리는 하나뿐이다. 티켓 세션 여럿이 각자 merge 하면 경합으로 같은 충돌이 반복되고, 한 세션이 충돌을 푸는 도중 다른 세션이 `MERGE_HEAD`를 지워 머지 기록 없는 커밋이 될 뻔했다(2026-10-01).

```
사람 ⇄ 허브(이 세션) ── spawn ──→ 티켓 dev 세션 (티켓 하나, new→wait→[done]이면 notify done)
          │          ←─ done ────            └─→ 워커 워크트리
          └ merge(순서대로, 판정은 verify.sh) ── tell "머지됨 <sha>" ──→ 티켓 세션이 요약 → notify decision
```

## 허브가 하지 않는 것

허브가 판단을 시작하면 코디네이터가 되고 두 번째 게이트가 생긴다. 그래서 아래는 금지다.

- **다음 티켓 발사를 판단하지 않는다.** 발사 가능 여부는 `ticket.sh ready`가 계산한다(의존 close + 스펙 미정 표시 0 + 동시 실행 < `TICKET_WIP`). 허브는 그 목록을 발사만 한다
- **리뷰 보고서·verify 로그 본문을 읽지 않는다.** 읽는 것은 티켓 세션이 쓴 티켓 폴더의 `summary.md`뿐이다. 허브 컨텍스트가 티켓 수만큼 불어나지 않게 하기 위해서다
- **재요청 본문을 쓰지 않는다.** 사람의 말을 그대로 `tell`로 넘긴다. 본문은 티켓 세션이 쓴다
- **close를 스스로 하지 않는다.** 사람이 "마무리"라고 말한 티켓만 close한다. close가 다음 티켓의 발사 조건이기 때문이다(사람이 판단을 위임하면 그 범위 안에서만 허브가 정한다)
- **충돌을 코드 쪽으로 풀지 않는다.** 머지 충돌이 공용 문서·정본 표의 줄 덧붙임이면 허브가 양쪽을 살려 푼다. 코드 파일이 충돌하면 머지를 되돌리고 워커에게 최신 dev를 합치라고 재요청한다
- **상태를 기억에 두지 않는다.** 매번 `board`로 파일에서 읽는다. 허브 세션은 언제 닫고 새로 열어도 같아야 한다

## 시작

```sh
sh ../.githooks/ticket.sh hub      # 이 터미널을 허브로 등록 (세션을 새로 열 때마다)
sh ../.githooks/ticket.sh board    # 상태표
```

`.tickets/`는 단일 작업과 묶음 작업이 폴더부터 갈린다. 티켓 하나의 정보는 그 티켓 폴더 하나에만 있다.

```
.tickets/
  queue.md · hub.terminal          공용
  single/<slug>/                   단일 작업 (허브 밖, ticket.sh new 를 직접)
  bundles/<묶음>/plan.tsv           묶음 작업의 하위 티켓 목록: id<TAB>브랜치<TAB>의존(쉼표, 없으면 -)<TAB>제목
  bundles/<묶음>/<브랜치>/           하위 티켓: spec.html(사람) · review-*·verify-*(훅) · session · summary.md · inbox.md · closed
```

묶음이 없으면 사람에게 계획 문서의 티켓 표를 `bundles/<묶음>/plan.tsv`로 옮겨도 되는지 묻는다. 브랜치는 `/` 없이 쓰고 앞에 묶음 약칭을 붙인다(`feat-cfd-t01-…`). 스펙은 `bundles/<묶음>/<브랜치>/spec.html`이고 **사람이 쓴다**(`writing-ticket-specs`). 티켓은 `<묶음>/<id>`로 가리킨다. 묶음이 하나뿐이면 `<id>`만 써도 된다.

## 루프

1. `ready <묶음>`이 출력한 id를 남은 자리만큼 `spawn <묶음>/<id>`
2. `hub-wait` — 티켓 세션의 알림을 기다린다. 빈손은 실패가 아니다. 다시 기다린다. 티켓 세션이 핸들 문제로 알리지 못할 수 있으니 `git log -1 <브랜치>`의 `[done]`도 같이 본다
3. 알림(`<묶음>/<id> <상태>`)이 오면 상태별로:
   - `done`: **허브가 머지한다.** `ticket.sh merge <브랜치>`. 한 번에 하나씩 — 다른 머지가 끝난 뒤에 다음을 돌린다
     - 통과 → `tell <묶음>/<id>`로 "머지됨 <머지 커밋 sha>, 보고서로 요약해 decision으로 알려라"
     - 충돌 → 위 "충돌을 코드 쪽으로 풀지 않는다" 규칙대로. 문서만이면 풀고 `git commit --no-edit`(pre-commit 게이트가 verify) 뒤 같은 `tell`
     - 게이트 실패 → `merge`가 이미 되돌렸다. verify 로그 경로를 `tell`로 넘겨 요약을 받는다
   그 밖의 상태는 그 티켓 폴더의 `summary.md`를 사람에게 보여 준다:
   - `decision`: 요약 그대로. 마지막 줄의 "재요청 / 마무리" 선택지를 사람에게 묻는다
   - `question`: 워커가 묻는 것이다. 사람의 답을 받는다
   - `failed`·`stalled`: 이유를 보여 주고 어떻게 할지 묻는다
4. 사람의 결정을 옮긴다:
   - 마무리 → **문서 반영** 뒤 `close <브랜치>`(브랜치는 plan.tsv 2열). 출력의 "새로 발사 가능"을 1로
     - 문서 반영: 워커는 공용 문서(작업 로그·위키·해시 대장·추적표·계획 진행 기록)를 고치지 않는다. 그 티켓의 `[done]` 커밋 본문들의 `문서 반영:` 절과 머지 diff를 근거로 **서브에이전트 하나**에게 반영시킨다(허브 컨텍스트에 diff를 싣지 않는다). 결과는 dev 의 비머지 커밋 하나다. lint 문제 0건·대기 0건을 확인한다
   - 재요청·답 → 사람의 말을 파일로 써서 `tell <묶음>/<id> <파일>`. 판단을 보태지 않는다
5. 2로

## 보고 형식

사람에게 하는 보고는 `writing-korean-explainers`의 `규모가 작은 보고` 형식이다. 여러 티켓을 한 번에 알릴 때는 `board` 출력을 티켓당 한 줄로 줄이고, 결정을 기다리는 티켓을 맨 위에 둔다.

## 막혔을 때

| 증상 | 확인 |
|---|---|
| `spawn`이 "발사 불가 상태=spec-tbd" | 스펙에 `<mark class="tbd">`가 남았다. 사람이 정할 칸이다 |
| `spawn`이 "동시 실행 상한" | 정상. close를 기다린다. 사람이 원하면 `TICKET_WIP=4 sh ../.githooks/ticket.sh spawn <묶음>/<id>` |
| 티켓 세션이 알림 없이 오래 조용함 | `orca terminal show --terminal $(cat .tickets/bundles/<묶음>/<브랜치>/session)`로 화면을 본다. 브랜치에 `[done]`이 있으면 허브가 merge 한다 |
| `wait`·`notify`가 "핸들을 못 찾았다" | `ORCA_TERMINAL_HANDLE`·`ORCA_PANE_KEY`가 terminal list 와 안 맞는다. 티켓 세션은 브랜치 커밋으로 `[done]`을 확인하고 summary.md 만 남긴다. 핸들을 직접 지정하는 우회는 만들지 않는다 |
| 머지마다 같은 공용 문서가 충돌 | 워커가 공용 문서를 고쳤다. 재요청에 "공용 문서는 고치지 말고 `문서 반영:`에 적어라"를 넣는다 |
| `tell`이 tui-idle 시간 초과 | 티켓 세션이 아직 일하는 중이다. 알림을 받은 뒤에 보낸다 |
| 티켓 세션이 "`send` 거부: already has an active dispatch"로 답을 못 넘김 | 워커가 질문(decision_gate) 뒤 worker_done 없이 턴을 끝내 앞 dispatch 가 열려 있다. 2026-10-02부터 `send`가 워커가 쉬면 앞 task 를 completed 로 닫고 다시 보낸다. 워커가 일하는 중이면 tui-idle 시간 초과로 끝나니 다음 알림 뒤에 다시 `tell` |
